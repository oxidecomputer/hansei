= Hansei

> https://en.wikipedia.org/wiki/Hansei[Hansei] (反省; "self-reflection") is a central idea in Japanese culture, meaning
to acknowledge one's own mistake and to pledge improvement.

A tool to inspect where we have erred with `tokio`: it reads the state of a tokio multi-threaded runtime from an
illumos core dump or live process, using debug information produced from a *separate* build of the same sources.
Currently a proof-of-concept, expect bugs.

WARNING: DO NOT RUN THIS AGAINST A PROCESS YOU CARE ABOUT. Live inspection stops the process while reading; the
`-w`/`--destructive` flag acknowledges that.

There are two debug-info backends:

* *Bundles* (recommended; targets built with rustc ≥ 1.97): `exegesis extract` reads a debug binary's DWARF and
  writes a compact bundle describing the async runtime. Task futures are joined between the debug binary and the
  target by their v0-mangled symbol names, so tasks are selected by id and their await chains are recovered fully
  automatically.
* *CTF* (legacy): generated by the `dwarf2ctf` tool in this workspace; task addresses and concrete future type
  names must be supplied by hand.

== Building

Building `hansei` itself requires `bindgen`, which in turn uses `libclang`. Ensure that the following are set, adjusting the LLVM version as-needed:

[source,shell]
----
export LIBCLANG_PATH=/opt/ooce/llvm-15/lib
export LD_LIBRARY_PATH=/opt/ooce/llvm-15/lib:$LD_LIBRARY_PATH
----

== Bundles

Build a *debug binary*: the same commit, toolchain, and flags as the target binary, compiled with full debug
information (an optimized profile with `debug = true`). Both compilations then contain the same monomorphizations
under the same v0-mangled names — the join key that lets layouts from one binary interpret memory from the other.
See `docs/v0-mangling-spike.md` for the pinned recipe and its caveats.

Extract the bundle (cross-platform; run it wherever the debug build happens):

[source,shell]
----
cargo run --release -p exegesis -- extract ${PATH_TO_DEBUG_BINARY} -o app.bundle
----

List the runtime's tasks, from a core dump or a live process:

[source,shell]
----
hansei tasks --bundle app.bundle --core ${PATH_TO_CORE}
hansei tasks --bundle app.bundle --pid ${PID} -w
----

Each task is listed with its id, lifecycle state, concrete future type, spawn location, and where the future is
defined. Trace one task's await chain:

[source,shell]
----
hansei task-trace --bundle app.bundle --core ${PATH_TO_CORE} --task-id ${ID} -v
----

This prints every future in the chain with its suspend state and the source line of the awaited expression;
`-v` adds the live locals at each await point. When the chain bottoms out in a recognized wait primitive, hansei
also reports what the task is actually waiting on:

* `tokio::time::Sleep` — the registered timer deadline;
* `JoinHandle<T>` — the id of the awaited task (a dependency edge between tasks);
* `tokio::sync::batch_semaphore::Acquire` — the contended `Mutex`/`RwLock`/`Semaphore` and its permit counts.

At attach time the bundle's symbol fingerprint is resolved against the target's symtab; anything less than a
100% match is refused (`--force` to override) so a wrong bundle can never silently misinterpret memory. Should
the TLS-key runtime discovery fail, `--heuristic-discovery` falls back to the legacy byte-pattern scan.

`hansei snapshot` captures everything a bundle-backed analysis reads from a target into a small replayable file;
together with a bundle extracted from a *separate* build it feeds the offline two-binary tests in
`hansei-types/tests`.

== CTF (legacy)

The CTF path supports the `tokio` runtime as configured in `omicron`, unstable features enabled, versions
1.48 and 1.49. The CTF file must be generated by the `dwarf2ctf` tool in this workspace.

You will need to build an optimized copy of the target binary with full debug information enabled.

[source,toml]
----
[profile.release]
debug = true
----

In theory a dev build should work, but they don't. I haven't run down why this is, I wouldn't expect the struct layout
to be different for them. The CTF can be applied to any binary that uses the same `tokio` version and features, i.e.,
you can use the same file for both `nexus` and `sled-agent`.

To generate the CTF file, execute:

[source,shell]
----
cargo run --release --bin dwarf2ctf -- ${PATH_TO_BINARY} --ctf-out tokio.ctf -t 'tokio::runtime::context::Context' -t 'tokio::runtime::task::core::Trailer' -t 'core::panic::location::Location' -t 'alloc::sync::Arc<tokio::runtime::park::Inner, alloc::alloc::Global>'
----

The CTF-backed subcommands:

* `scheduler-dump` (alias `dump`) will output the state of the `tokio` runtime scheduler and thread-local contexts from either a core dump or
a live process. For example:
+
[source,shell]
----
cargo run --release --bin hansei -- dump --core ${PATH_TO_CORE} --ctf ${PATH_TO_CTF}
----
* `poll` will attach to the process, periodically pausing it at to read the `tokio` state, printing a brief summary.
+
[source,shell]
----
cargo run --release --bin hansei -- poll --pid ${PID} --ctf ${PATH_TO_CTF}
----
* `task-trace` with `--ctf` requires the task address (from a prior `scheduler-dump`) and the concrete future type
name to be supplied with `--addr`/`--type`; the bundle path resolves both automatically.

Backtraces for all threads are captured by default by `dump`, though only displayed for active workers. This is quite
slow currently and disabled for `poll`.

=== Why generate CTF for these types?

To give a bit of explanation on why these types are being included. Any type that is linked to a member of a type
requested will be included in the CTF. `tokio` and `std::task::Waker` are a bit unusual for Rust as they will sometimes
use an bare offset or `void*` to access a value. Types referenced this way do not have a cross-reference in the DWARF,
so we need to manually tell `dwarf2ctf` to include them.

* `tokio::runtime::context::Context`: The thread-local context for workers. Pulls in the vast majority of types we
need, including the scheduler.
* `tokio::runtime::task::core::Trailer`: The cold data stored at the end of a task. The offset to this is stored in the
`TaskHeader`. Contains the `Waker` for the task.
* `core::panic::location::Location`: The source location that generated the future. Also stored as an offset from the
`TaskHeader`.
* `alloc::sync::Arc<tokio::runtime::park::Inner, alloc::alloc::Global>`: One of the types potentially stored as a
`void*` in a `Waker`. Tracks the state of a thread.

== Testing

* `cargo test` — cross-platform unit tests and the offline two-binary snapshot tests.
* `tests/illumos/run.sh` — the on-box integration suite: it builds two-binary fixture pairs, cores and
live-attaches real programs, checks exact await-chain goldens (including the RFD 609 futurelock shape), and runs
a CTF↔bundle differential against the same cores.
