= Durin

A suite of tools for extracting DWARF-derived *debug bundles* from Rust
binaries and using them to reconstruct the runtime state of a live (or cored)
`tokio` process.

Experimental and mostly untested, expect bugs.

== Tools

These are the workspace members that may be useful:

* exegesis: Read a debug binary's DWARF and extract a self-contained *debug
  bundle* describing its async runtime and types; also the bundle format's
  reader and type views.
* hansei: Inspect the state of the `tokio` multi-threaded runtime in a core
  dump: task listings, automatic await-chain traces, and task dependency
  graphs with futurelock detection.
* hansei-types: The tokio-introspection library behind hansei.
* reify: Interpret a process's memory through a debug bundle, rendering values
  of the bundle's types for humans.
* proc: Target access — readers for illumos and Linux core dumps, minimal
  bindings for illumos `libproc`, and replayable target snapshots.
* durin: Read and write CTF files.

A core is read according to what wrote it rather than what is reading it, so an
illumos core opens on Linux and a Linux core opens on illumos. hansei inspects
cores only; take one with `gcore` and point hansei at it. Bundle extraction
(exegesis) and type/value work (reify) are portable.

== Usage

The workflow has two stages: extract a bundle once from a debug binary
(anywhere), then point hansei at a matching target.

=== 1. Extract a bundle (exegesis)

Read the DWARF from a debug build and write a bundle:

[source,sh]
----
exegesis extract path/to/sled-agent.debug -o sled-agent.bundle
----

The bundle is self-contained; the debug binary is not needed again. Other
subcommands inspect what was produced:

[source,sh]
----
exegesis stats sled-agent.bundle   # summary counts
exegesis dump  sled-agent.bundle    # full tables as text
----

`extract --include-type <fqn>` forces an otherwise-unreached type to be
emitted, and `--allow-missing-infra` lets extraction proceed on a binary that
isn't a tokio target.

=== 2. Inspect a target (hansei)

hansei reads a core dump (`--core`) written by either system, interpreting it
through the bundle from step 1. Those two files are all the command line takes:
they name a *session*, and what to ask of it is read from stdin.

[source,sh]
----
hansei --core core.sled-agent --bundle sled-agent.bundle
----

When stdin is a terminal that is a prompt, with history, tab completion, and
errors that end the command rather than the session:

----
hansei〉tasks                    # every task: id, state, future type, spawn site
hansei〉trace 42 -v              # one task's await chain, with its live locals
hansei〉graph                    # the dependency graph, and any futurelock
hansei〉threads                  # the runtime's threads: worker cores and stacks
hansei〉shared-state             # the scheduler state the workers share
hansei〉drivers                  # the io, signal and time drivers
hansei〉find-types oxide         # bundle type names containing a substring
hansei〉type sled_agent::Foo     # one type's recorded layout
hansei〉type -r sled_agent::Foo  # that layout with everything it names in it
hansei〉info                     # what is attached, and how well it matches
hansei〉tasks ! grep sled_agent  # pipe a command's output into a shell command
hansei〉tasks ; graph            # several commands, in order, on one line
hansei〉quit
----

`trace` takes `--depth`/`-d` to bound how deep values are formatted, and the
graph flags any futurelock — a lock future granted or queued on a contended
semaphore whose task stopped polling it (RFD 609). `threads`, `shared-state`
and `drivers` read the runtime's own state out of the target and take the same
`--depth`; `find-types` and `type` ask the bundle instead of the target, and
report the layouts every other command decodes memory with — `type` stops at
the names a layout mentions, `type --recursive`/`-r` opens each of them under
the line that names it, and whatever they name in turn, four deep unless
`--depth` says otherwise, marking with a `…` every line it had more to say
below. A command answers to any leading substring that fits it and no other,
so `sh` runs `shared-state`. Every flag has a short form; `help` lists the
rest.

When stdin is not a terminal the same commands are read one per line, which is
how scripts and pipelines drive it; `--exec`/`-e` gives them on the command
line instead, and the session exits when they are answered:

[source,sh]
----
echo 'trace 42 -v' | hansei --core core.sled-agent --bundle sled-agent.bundle

hansei --core core.sled-agent --bundle sled-agent.bundle -e 'tasks; graph'

hansei --core core.sled-agent --bundle sled-agent.bundle <<'EOF'
# blank lines and comments are skipped
tasks
graph
EOF
----

Either way the session stops at the first command that fails and exits
non-zero; `quit` ends it early.

The session takes `--force`/`-f` to proceed even when the bundle's symbols don't all
resolve in the target (a bundle from a mismatched build otherwise refuses to
attach); `trace` takes `--ugly`/`-u` to bypass the custom value formatters and
show the raw structural view.

== What's with the name?

In _The Lord of the Rings_, Durin is Gimli's father, `gimli` being the excellent DWARF library for Rust. The joke doesn't quite work as
DWARF is actually older than CTF, oh well.
